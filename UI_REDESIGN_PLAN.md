# UI/UX Redesign: reportes, shared, horarios

## Context

The `solicitudesActividades` module (list, `Solicitud` detail, `ConversacionChat`, `CrearSolicitud`) was already redesigned to a consistent "glass" design language, and the lessons from that rollout were captured in `.claude/skills/interno-ui-system/SKILL.md`. The `reportes`, `shared`, and `horarios` modules were never brought in line — each grew its own ad-hoc styling independently (mostly pre-dating the glass system, in `horarios`'s case with a completely bespoke navy/amber palette duplicated across 7+ files). This plan applies the established design system to all three, **UI/UX only — no logic, no data-flow, no field/behavior changes.**

This file is the durable plan for a **future session** to pick up and implement. It is not being executed in the session that wrote it.

**Skills to load before implementing (in this order):**
1. **`interno-ui-system`** (primary playbook, `.claude/skills/interno-ui-system/SKILL.md`) — layout shape (header → bounded top → flex thread → pinned composer), header conventions (neutral-gray back button vs accent-blue action buttons, vertical-centering Android fix), list/card conventions (translucent glass card recipe, no separators between bordered cards, action-required emphasis via brightness not opacity-dimming), the blanket "modals solid / page content glass" rule, `GlassTabSelector` usage, and the verification checklist (§9).
2. **`glass-ui-rollout`** — mechanics for converting an existing complex screen (cards, lists, modals — not a simple form) to glass tokens: mapping the reachable surface, extending `shared/ui/glass.ts` if a new token is genuinely needed, the Android `elevation` + translucency trap, execution order.
3. **`glass-ui`** — the simple-form visual recipe (gradient background, translucent inputs, no icons); relevant mainly to `shared/views/CambiarContrasenaView.tsx` and `CrearUsuario.tsx`, which are themselves the two reference implementations this skill points to.
4. **`input-focus-style`** — reused wherever a redesigned screen has a `TextInput` that needs the app's custom focus-ring treatment instead of the browser default (horarios search boxes, reportes forms, `AsociarCuenta`/`EditarUsuario` fields).

## Findings summary (from Explore pass, already done — don't redo this research)

Three parallel Explore agents read every file in scope in the session that wrote this plan. Key facts driving the plan below:

- **Zero files in `reportes/` or `horarios/` use `glassColors`/`glassStyles`/`GlassTabSelector`.** Only one file across both modules (`TurnoScanCard.tsx`) touches the glass system at all (partial: `glassStyles.card` + `GlassButton`).
- **`shared/ui/glass.ts` is already fixed** (per the git diff at plan-writing time): `modalCard` is solid `#ffffff`, not translucent — the blanket "solid modals" rule is already satisfied at the token source. Every modal encountered in all three modules is already solid/opaque in practice (arrived at independently, not via the token) — nothing to *undo*, just route through the shared token instead of ad-hoc hex.
- **`shared/views/CambiarContrasenaView.tsx` and `CrearUsuario.tsx` are already fully glass-compliant** — they're the two reference implementations the `glass-ui` skill itself cites. Minimal touch needed (swap local `Pressable`+`glassStyles.button` for the actual `GlassButton` component — reuse, not restyling).
- **`shared/views/AsociarCuenta.tsx`, `DetalleEmpleado.tsx`, `EditarUsuario.tsx`** are fully ad-hoc (`Colors['light']`, `elevation`+solid-white cards, hand-rolled tab bar in `DetalleEmpleado` instead of `GlassTabSelector`). `AsociarCuenta.tsx` also has a real §2 violation: a `FlatList` with `scrollEnabled={false}` nested inside an outer `ScrollView`.
- **`shared/ui/AppBackButton.tsx`** currently renders accent-blue (`colors.lightTint`), contradicting the skill's neutral-gray-back-button rule. It has exactly **one** consumer (`app/(extras)/_layout.tsx`, the shared Stack header for the whole `(extras)` group) — low blast radius, safe single-point fix that will also correctly re-color the back button on every `(extras)` screen, including reportes and horarios routes that ride this same Stack header.
- **`reportes/`**: status-color logic (`getEstadoColor`) is independently duplicated 3× across `MisReportes.tsx`/`ReportesEmpleado.tsx`/(absent, inconsistent, in) `ReporteModal.tsx`, which instead renders a single monochrome badge regardless of estado — a real visual inconsistency between list and detail view of the same data. Four different list-rendering mechanisms are used across the module (`OwnFlatList`, manual `ScrollView`+`.map()`, raw `FlatList`, `.map()` inside a non-scrolling `View`). `ReporteModal.tsx` (624 LOC) and `CrearReporte.tsx` (655 LOC) are the two largest files and don't follow the full §2 layout shape (form/action content is one big outer scroll, not header→bounded→thread→pinned-action). Two files have dead/unused leftover styles (`fab*` in `CrearReporte.tsx`, `header*` in `CrearReporteEncargado.tsx`).
- **`horarios/`**: `GestionHorarios.tsx` (857 LOC, largest file in either module) and `HorasExtras.tsx` (528 LOC) both put filter chrome *and* the list inside one outer `ScrollView` with an absolutely-positioned footer — the exact anti-pattern §2 warns about. Both hand-roll a search box (keeping the magnifying-glass icon the skill says `SearchBar` should not have) and a segmented turno filter, instead of reusing `SearchBar`/`GlassTabSelector`. The same bespoke hex palette (navy `#2b1f5c`, blue `#2f86d6`, amber `#c98a1a`, `LINE`/`MUTED`/`INK`/`CARD`, etc.) is copy-pasted verbatim into 7 separate files. A toast implementation is duplicated verbatim between `GestionHorarios.tsx` and `HorasExtras.tsx`. Sheets split across two mechanisms: `TurnoDetalle`/`DetalleHorasExtraSheet` use `FullScreenPortal`; `EditarTurnoSheet`/`LiquidarAmountModal` use a raw RN `Modal`. All are already solid/opaque (nothing to fix there). `HorariosHome.tsx`'s custom back button is accent-blue, inconsistent with the rest of the module's sheets, which are already neutral gray.

## Scope decision: phased delivery

Given the combined size (~2,600 LOC in `reportes`, ~3,650 in `shared`, ~3,525 in `horarios` — about 30 files total), this should be delivered as **three sequential phases**, each independently reviewable/committable, in this order:

**Phase 1 — `shared`** (foundation first, since `AppBackButton` and the glass tokens it and every other module rides on live here; also the smallest *net-new* effort since 2 of 5 views are already compliant)
**Phase 2 — `reportes`** (medium size, clear duplication to clean up, self-contained)
**Phase 3 — `horarios`** (largest and most legacy; benefits from patterns established in Phases 1–2, especially the card recipe and search/filter reuse)

Each phase ends with the full verification checklist (below) before moving to the next.

## Phase 1: `shared`

1. **`shared/ui/AppBackButton.tsx`** — recolor from `colors.lightTint` (accent blue) to the skill's neutral-gray pill recipe (`rgba(17,24,28,0.03)` fill / `rgba(17,24,28,0.12)` border, `glassColors.textMuted` icon), matching what `TurnoDetalle.tsx`/`DetalleHorasExtraSheet.tsx` already do independently. Single consumer (`app/(extras)/_layout.tsx`) — this one edit fixes the back button on every `(extras)` route at once, including reportes/horarios screens touched in later phases.
2. **`shared/views/CambiarContrasenaView.tsx`, `CrearUsuario.tsx`** — light touch only: replace the local `Pressable` + `glassStyles.button`/`buttonSecondary` wrapping with the actual `GlassButton` component (`shared/ui/GlassButton.tsx`) for consistency of the underlying primitive. No layout change (both already match the `glass-ui` auth-form shape).
3. **`shared/views/DetalleEmpleado.tsx`** — convert the hand-rolled underline tab bar to `GlassTabSelector` (`components/ui/GlassTabSelector.tsx`, already generic over N tabs: reportes/permisos/francos/vacaciones). Convert card/section chrome (comparison cards, selection badges) from `Colors['light']`+`elevation` to `glassStyles.card`. Leave the routing/params logic (`comparingWith`, `source`, `selectedUsers`) untouched — this screen has the highest blast radius in the module (5 call sites from `reportes/`), so structural/prop changes are out of scope, visual-only in place.
4. **`shared/views/EditarUsuario.tsx`** — convert the two stacked form "card" sections from `elevation`+solid-white to `glassStyles.card`/`fieldGlass` tokens; apply `input-focus-style` to its `InputWithIcon` fields. `OperacionPendienteModal` overlay is already glass-compliant, untouched.
5. **`shared/views/AsociarCuenta.tsx`** — the largest file (744 LOC) and the one real structural fix in this phase: the cuenta-selection `FlatList` (`scrollEnabled={false}`) is nested inside the outer `ScrollView`. Per §2, restructure so the account-selection list owns its own `flex: 1` scroll region instead of being flattened into the page scroll (bounded step content above, scrollable list below, matching the header→bounded→thread shape). Convert per-step card/form chrome to glass tokens; fix the mojibake/corrupted icon literal noticed in the CUIT step. Apply `input-focus-style` to its inputs.

## Phase 2: `reportes`

1. **Centralize status-color mapping**: create one shared `getEstadoColor`/status-badge helper (visual mapping only — `estado → {color, backgroundColor}` — not a logic/behavior change) and use it in `MisReportes.tsx`, `ReportesEmpleado.tsx`, and `ReporteModal.tsx`'s currently-monochrome badge, so the detail view and list views agree on how each `estado` renders. Fold the unofficial 4th color (`#9C27B0` "desestimado"/purple) into this single source instead of being a magic hex repeated 3×.
2. **`ReporteModal.tsx`** (624 LOC) — restructure to the §2 shape: header (apply neutral-gray back-button pill, matching Phase 1's `AppBackButton` fix) → bounded metadata section (info grid, status badge) → scrollable thread (description, gallery, bitácora) → the "Modificar estado" form's `GlassButton` pinned as a fixed sibling after the scroll, not scrolling away with it. Route colors through `glassColors`/`glassStyles` instead of raw hex (`#fff`, `#f9fafb`, `#999`, etc.).
3. **`CrearReporte.tsx`** (655 LOC) — already has the pinned-action-outside-scroll pattern; bring the rest in line: swap raw `KeyboardAvoidingView` for the shared `ModalKeyboardView` (matching `ReporteModal.tsx`), route the image-action button borders through `glassColors`/`glassStyles.button` instead of the coincidentally-matching hardcoded `rgba(26,115,232,0.35)`, give the date/time pseudo-buttons real pill chrome consistent with the image-action buttons, remove the dead `fab*` styles, apply `input-focus-style` to text fields.
4. **`MisReportes.tsx`, `ReportesEmpleado.tsx`** — convert list cards to the shared translucent glass card recipe (`glassStyles.card`, no `elevation`); in `ReportesEmpleado.tsx`, drop the manual `Separator` between cards now that cards carry their own border (§4); standardize both on `OwnFlatList` (already used by `MisReportes.tsx`) instead of `ReportesEmpleado.tsx`'s manual `ScrollView`+`.map()`. Add a real (non-blank) empty-error state to both instead of the current silently-blank `View`.
5. **`Semaforo.tsx`** — convert zone-section/item card chrome to glass tokens; leave the semantic zone/status colors (`colors.error`/`warning`/`success`) untouched per the "semantic colors never glass-ified" rule — only the *container* shape changes. Route the zone-count pill's ad-hoc `rgba(255,255,255,0.2)` through `glassStyles.pill`.
6. **`TopEmployee.tsx`, `UpgradedEmployee.tsx`** — restyle the stat cards onto `glassStyles.card`, replacing the solid-white+static-border recipe; keep the semantic green/purple accent colors as-is (they're identity accents on a card, not container glass).
7. **`CrearReporteEncargado.tsx`** — convert the search-results `FlatList` rows to consistent glass-card styling if warranted, or leave as plain rows if it reads better without cards (this list is a user picker, not content — use judgment during implementation, default to plain rows with the hairline `ItemSeparatorComponent` kept since there are no card borders to conflict with). Remove the dead `header*`/`headerTitle`/`iconButton` styles. Fix the same `colors.lightTint + '15'` banner opacity hack to use a real glass token.

## Phase 3: `horarios`

1. **Centralize the duplicated palette**: create one `features/horarios/theme.ts` (or extend `shared/ui/glass.ts` if genuinely generic — per `glass-ui-rollout`'s guidance to fix tokens once, not per-file) holding the navy/amber/line/muted/ink/card constants that are currently copy-pasted verbatim across `GestionHorarios.tsx`, `HorasExtras.tsx`, `TurnoCard.tsx`, `EmpleadoHorasExtraCard.tsx`, `EditarTurnoSheet.tsx`, `DetalleHorasExtraSheet.tsx`, `LiquidarAmountModal.tsx`. Replace the hand-rolled search box (which keeps the magnifying-glass icon) with the shared `SearchBar` component. Replace the hand-rolled Todos/Mañana/Tarde segmented toggle with `GlassTabSelector`. 8. **`TurnoDetalle.tsx`** — already closest to compliant (uses `FullScreenPortal`, already-correct gray back button); just route its mixed theme-token/hardcoded-hex colors and `colors.success + 'NN'` opacity-hack badge through real glass tokens.
9. **`TurnoScanCard.tsx`** — already the most-migrated file (uses `glassStyles.card` + `GlassButton`); finish the job by routing its remaining `colors.lightTint`/opacity-hack usages through `glassColors`.

## Verification (run after each phase, per skill §9)

1. `grep -n "elevation"` every touched file — confirm no hit shares a style object with a translucent (`rgba(...,` alpha < 1) `backgroundColor`.
2. `tsc --noEmit` before vs after (`git stash`/`git stash pop`), compare error *counts* — zero new errors.
3. `npx expo export --platform web --output-dir <scratchpad>` to confirm Metro resolves/compiles every touched file with no import/syntax breakage; delete the output afterward.
4. Grep for now-orphaned styles/refs/props after any structural edit (e.g. the `AsociarCuenta.tsx` nested-FlatList fix, the `GestionHorarios`/`HorasExtras` scroll-region split).
5. Explicitly call out what can't be visually verified from this environment (no simulator/device access) — Android `elevation` drop and real font/vertical-centering rendering — rather than claiming full confidence.
6. No logic/data/behavior changes anywhere — diff review should show only `style`/JSX-structure/import changes plus the (behavior-neutral) status-color/palette centralization noted in Phases 2–3.
